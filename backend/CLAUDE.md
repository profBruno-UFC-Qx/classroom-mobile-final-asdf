# CLAUDE.md

## Project

SaaS backend API. Go + chi router (v5) + PostgreSQL with plain SQL (no ORM). Uses `database/sql` with `lib/pq` driver. API documentation generated with `github.com/swaggo/swag` and served at `/swagger/index.html` in development.

## Commands

All commands below must be run from `backend/` unless noted otherwise.

```bash
make dev    # Start docker services (postgres + redis) and air (hot reload) in one command
make down   # Stop air process and docker services
```

Run from `backend/`:

```bash
go test ./...                        # Run all tests
go test ./... -v -count=1            # Verbose, no cache
go test ./internal/user/...          # Test a single domain
go vet ./...                         # Static analysis
golangci-lint run                    # Lint
go run ./cmd/migrate up              # Run DB migrations
go run ./cmd/migrate down            # Rollback last migration
go run github.com/swaggo/swag/cmd/swag init --generalInfo cmd/api/main.go --output docs/swagger --outputTypes go,json,yaml  # Regenerate Swagger docs
```

## Development

**Go version:** 1.24

Use `air` for hot reload during development. It watches all `.go` files under `internal/` and `cmd/` and rebuilds/restarts the server automatically on save. Config is in `backend/.air.toml`. The compiled binary is written to `backend/tmp/` (gitignored). Use `make dev` to start everything in one command.

## Code style

- Functions: 4-20 lines. Split if longer.
- Files: under 500 lines. Split by responsibility.
- One thing per function, one responsibility per module (SRP).
- Names: specific and unique. Avoid `data`, `handler`, `Manager`.
  Prefer names that return <5 grep hits in the codebase.
- Types: explicit. No `any`, no `Dict`, no untyped functions.
- No code duplication. Extract shared logic into a function/module.
- Early returns over nested ifs. Max 2 levels of indentation.
- Exception messages must include the offending value and expected shape.

## Comments

- Keep your own comments. Don't strip them on refactor — they carry
  intent and provenance.
- Write WHY, not WHAT. Skip `// increment counter` above `i++`.
- Docstrings on public functions: intent + one usage example.
- Reference issue numbers / commit SHAs when a line exists because
  of a specific bug or upstream constraint.

## Structure

- Follow the framework's convention (Rails, Django, Next.js, etc.).
- Prefer small focused modules over god files.
- Predictable paths: controller/model/view, src/lib/test, etc.

## Logging

- Structured JSON when logging for debugging / observability.
- Plain text only for user-facing CLI output.

## Architecture

Clean Architecture with 3 layers: **Handler → Service → Repository**. Dependencies always point inward (handler depends on service interface, service depends on repository interface).

```
project-root/
├── cmd/
│   ├── api/                  # Application entrypoint (main.go)
│   ├── migrate/              # Migration runner CLI
│   └── seed/                 # Database seeder
│
├── internal/
│   ├── domain/               # Shared domain types used across features
│   │   └── errors.go         # App-level error types (ErrNotFound, ErrConflict, etc.)
│   │
│   ├── <feature>/            # One folder per domain feature (e.g., user/, billing/, project/)
│   │   ├── model.go          # Domain entity struct(s) only
│   │   ├── dto.go            # Input structs and filter types (DTOs)
│   │   ├── interfaces.go     # Repository and Service interface contracts
│   │   ├── handler.go        # HTTP handlers (chi handlers) — receives request, calls service
│   │   ├── handler_test.go   # Handler tests (mock the service)
│   │   ├── service.go        # Business logic — orchestrates repository calls
│   │   ├── service_test.go   # Service tests (mock the repository)
│   │   ├── repository.go     # Database access — plain SQL queries only
│   │   ├── repository_test.go # Repository tests (use sqlmock or test DB)
│   │   └── routes.go         # func RegisterRoutes(r chi.Router, h *Handler) — mounts this feature's routes
│   │
│   ├── middleware/            # Custom chi middlewares (auth, CORS, logging, etc.)
│   └── platform/
│       ├── database/          # DB connection pool setup, health check
│       └── config/            # Config loading (env vars)
│
├── migrations/                # SQL migration files: 001_create_users.up.sql / 001_create_users.down.sql
│
├── docs/
│   └── swagger/               # Auto-generated by swag (docs.go, swagger.json, swagger.yaml)
│
├── go.mod
├── go.sum
└── CLAUDE.md
```

## Layer Responsibilities

**Handler** (`handler.go`): Parses HTTP request (path params, query params, JSON body). Validates input. Calls the service. Writes the HTTP response. No business logic. No SQL. Equivalent to a "dumb component" — it only translates HTTP ↔ service calls.

**Service** (`service.go`): Contains all business rules and orchestration logic. Receives and returns Go structs, never `*http.Request` or `http.ResponseWriter`. Depends on repository through an **interface** defined in `interfaces.go`. This is where authorization checks, data transformations, and multi-step operations live.

**Repository** (`repository.go`): Executes plain SQL against PostgreSQL using `database/sql`. Returns domain structs. No business logic — only data access. Each query is a method. Use `$1, $2` placeholders (PostgreSQL syntax), never string concatenation.

## Conventions

- Every feature uses **three files for type definitions** — never mix them:
  - `model.go` — domain entity structs only (e.g. `User`, `Spending`)
  - `dto.go` — input structs and filter types (e.g. `CreateSpendingInput`, `SpendingFilter`)
  - `interfaces.go` — repository and service interface contracts
- Every feature defines its interfaces in `interfaces.go`:
  ```go
  type UserRepository interface {
      GetByID(ctx context.Context, id int64) (*User, error)
      Create(ctx context.Context, u *User) error
  }
  type UserService interface {
      GetByID(ctx context.Context, id int64) (*User, error)
      Register(ctx context.Context, input RegisterInput) (*User, error)
  }
  ```
- Dependency injection via constructors: `NewService(repo UserRepository) *Service`, `NewHandler(svc UserService) *Handler`.
- All handler functions have the signature `func(w http.ResponseWriter, r *http.Request)` — standard `net/http` compatible.
- Use `chi.URLParam(r, "id")` for path parameters.
- Use `context.Context` everywhere. Pass it from the handler through service to repository.
- Return domain errors from services (`domain.ErrNotFound`, `domain.ErrConflict`). Handlers translate these to HTTP status codes.
- JSON responses use a consistent envelope: `{"data": ...}` for success, `{"error": "message"}` for errors.
- File naming: `snake_case.go`. One struct/interface grouping per file.
- Feature registration in `cmd/api/main.go` follows this pattern:
  ```go
  userRepo := user.NewRepository(db)
  userSvc := user.NewService(userRepo)
  userHandler := user.NewHandler(userSvc)
  user.RegisterRoutes(r, userHandler)
  ```

## SQL and Migrations

- All SQL is hand-written. No ORMs. No query builders.
- Use `database/sql` with `lib/pq` driver.
- Use `db.QueryContext` / `db.QueryRowContext` / `db.ExecContext` — always pass `ctx`.
- Scan results into structs field by field. No reflection-based scanning.
- Migrations are plain `.sql` files in `migrations/` with `up` and `down` variants.
- Migration naming: `NNN_description.up.sql` and `NNN_description.down.sql` (e.g., `001_create_users.up.sql`).
- Always include `IF NOT EXISTS` / `IF EXISTS` in DDL when safe.
- Use transactions (`db.BeginTx`) for operations that touch multiple tables.

### Running migrations

Run from `backend/`:

```bash
go run ./cmd/migrate up    # Apply all pending migrations (runs every unapplied .up.sql in order)
go run ./cmd/migrate down  # Roll back the last applied migration (runs its .down.sql)
```

**Important:**

- `down` rolls back **one migration at a time** — the most recently applied one.
- Running `down` when the latest migration was not the one you intended to revert will roll back the wrong migration. Check the current state first if unsure.
- After rolling back, the backend code may reference columns/tables that no longer exist, causing 500 errors. Always keep the DB schema in sync with what the code expects.
- To check which migrations have been applied, query the `schema_migrations` table: `SELECT * FROM schema_migrations ORDER BY version;`

## Swagger / OpenAPI

Swagger UI is served at `http://localhost:8080/swagger/index.html` **only when `ENV=development`** (the default). It is completely disabled in production.

**MANDATORY: Every handler function MUST have a full set of swagger annotations.** No exceptions. Missing annotations will cause the generated docs to be incomplete.

After adding or changing any handler, regenerate the docs:

```bash
go run github.com/swaggo/swag/cmd/swag init --generalInfo cmd/api/main.go --output docs/swagger --outputTypes go,json,yaml
```

Required annotation template for every handler:

```go
// HandlerName one-line summary.
//
// @Summary      Short summary (shown in the route list)
// @Description  Full description of what this endpoint does.
// @Tags         feature-name
// @Accept       json
// @Produce      json
// @Param        id    path      int                    true  "Resource ID"
// @Param        body  body      SomeInputStruct        true  "Request payload"
// @Success      200   {object}  SomeResponseStruct
// @Failure      400   {object}  response.ErrorResponse  "Validation error"
// @Failure      401   {object}  response.ErrorResponse  "Unauthorized"
// @Failure      404   {object}  response.ErrorResponse  "Not found"
// @Failure      500   {object}  response.ErrorResponse  "Internal server error"
// @Router       /api/feature/path [method]
func (h *Handler) HandlerName(w http.ResponseWriter, r *http.Request) {
```

Rules:

- `@Tags` must match the feature folder name (e.g., `auth`, `user`, `billing`).
- `@Router` path must exactly match the chi route pattern (use `{param}` notation).
- Always document **all possible failure responses**, not just the happy path.
- Use `response.ErrorResponse` for all error `@Failure` entries.
- Keep `docs/swagger/` committed in version control.

## Tests

- Framework: Minitest + FactoryBot + Shoulda Matchers + SimpleCov
- Every new function gets a test. Bug fixes get a regression test.
- Mock external I/O (API, DB, filesystem) with named fake classes,
  not inline stubs.
- Tests must be F.I.R.S.T: fast, independent, repeatable,
  self-validating, timely.
- Every handler, service, and repository gets a `_test.go` file alongside it.
- **Handler tests**: mock the service interface. Use `httptest.NewRecorder()` and `httptest.NewRequest()`. Assert status codes and JSON response bodies.
- **Service tests**: mock the repository interface. Test business logic in isolation. No HTTP, no database.
- **Repository tests**: use `DATA-DOG/go-sqlmock` to mock `database/sql`. Assert correct SQL queries and parameter binding.
- Use table-driven tests (`[]struct{ name string; ... }`) for all test functions with multiple cases.
- Test function naming: `TestHandler_Create`, `TestService_Register`, `TestRepository_GetByID`.
- Use `testify/assert` for assertions.

## Commit Convention

Every commit must follow this pattern:

```
<type>(<backend|frontend|back&front> - <feature>): <short summary of what was done>

- <bullet explaining the first meaningful change>
- <bullet explaining the second meaningful change>
- ...
```

**Scope:**

- `backend` — changes only in the Go API
- `frontend` — changes only in the Angular app
- `back&front` — changes span both sides (e.g. a new endpoint consumed by the UI)

**Types:**

- `feat` — new feature or endpoint
- `fix` — bug fix
- `test` — adding or updating tests only
- `chore` — tooling, config, dependencies, docs

**Feature name** — use the domain folder name (e.g. `spending`, `auth`, `user`). For cross-cutting changes use `core`.

**Examples:**

```
feat(backend - spending): add date range filtering to GET /api/spendings

- Add SpendingFilter struct with optional From/To time.Time pointers
- Repository builds parameterized SQL dynamically; no user input concatenated
- Handler parses from/to query params (YYYY-MM-DD), returns 400 on bad format
- Swagger annotations updated with new query param docs
- Tests added across handler, service, and repository layers
```

## Do NOT

- Do NOT use an ORM or query builder. Write plain SQL.
- Do NOT put business logic in handlers. Handlers only parse/validate input and write output.
- Do NOT put HTTP concepts (`http.Request`, status codes, JSON encoding) in services or repositories.
- Do NOT use `any` or `interface{}` when a concrete type or named interface exists.
- Do NOT concatenate strings to build SQL queries. Always use parameterized queries (`$1, $2`).
- Do NOT skip writing `_test.go` files when creating new handlers, services, or repositories.
- Do NOT put input structs or filter types in `model.go` — use `dto.go`.
- Do NOT put interface contracts in `model.go` — use `interfaces.go`.
- Do NOT import one feature package from another feature package. If features share logic, extract it to `internal/domain/` or create a shared service.
- Do NOT add a handler without full swagger annotations — every handler must be documented.
- Do NOT forget to run `go run github.com/swaggo/swag/cmd/swag init ...` and commit the updated `docs/swagger/` after changing any handler signature, route, or request/response struct.

## Security

**Never do:**

- Expose internal IDs in public URLs
- Skip CSRF protection
- Store secrets in code (use ENV vars)
